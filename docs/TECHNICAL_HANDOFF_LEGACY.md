# TECHNICAL_HANDOFF.md

## 1. Executive summary

Audit date: 2026-08-29.

The current MVP is a real, deployed, database-backed application. It is not only a visual mock. It has a local source checkout, a Git repository, one commit, a Sites-managed remote repository, a private production deployment, a Cloudflare D1 database, API routes, database sessions, and persistent CRUD for a bounded subset of the original scope.

The preferred target architecture — GitHub → Vercel → Next.js → Neon PostgreSQL — is feasible without rebuilding the product from zero. The React UI, most App Router route shapes, TypeScript types, business vocabulary, forms, and a large portion of the business rules can be reused. The database adapter, SQL dialect, authentication hardening, deployment integration, cron processing, migrations, and several incomplete product modules need deliberate replacement or completion.

Important current facts:

- The live D1 database contains 12 user tables and **0 production records in every table** at audit time.
- The administrator and four default templates are runtime seeds, not migration seeds. They will only be inserted when an application authentication path first calls `ensureDatabase()`.
- The local Miniflare D1 database is separate from production and contains QA records from implementation testing. It must not be treated as production data.
- No DNS records were changed during this audit. `clientes.gabrielmisao.com.br` is attached to Sites but remains `pending_validation`; it does not currently route to the Site.
- No code, database, DNS, deployment, or authentication behavior was changed during the audit. This document is the only new artifact.

### Schema sources

There are currently three schema representations:

1. `db/schema.ts`: Drizzle SQLite schema declarations.
2. `drizzle/0000_wakeful_millenium_guard.sql` and `drizzle/0001_peaceful_radioactive_man.sql`: generated migration SQL.

## 7. Current login and session flow

### User storage and initialization

Users are stored in `users`. The only allowed administrator email is hard-coded in `lib/server-auth.ts`. `ensureDatabase()` runs DDL, inserts the administrator with `INSERT OR IGNORE`, then seeds four message templates.

The admin row is not present in the production database yet. It will be created when a login/session path first invokes `ensureDatabase()`.

### Password storage

The password is never stored in plaintext in the repository or database.

- Algorithm: PBKDF2 with HMAC-SHA-256.
- Iterations: 210,000.
- Output: 256 bits.
- Salt: Base64-encoded 16-byte salt for newly selected passwords.
- Database columns: `password_hash` and `password_salt`.
- The initial provisional password's precomputed hash and salt are hard-coded in source; the plaintext provisional password is not.

No repository match was found for the provisional plaintext password.

Security qualification: although not plaintext, placing a fixed initial hash and salt in source makes the provisional credential an immutable bootstrap secret target. If the provisional password is known before the first successful change, it can be tested offline against the committed hash. In the migration, bootstrap credentials should be provided through a one-time server-side seed/reset flow, not committed constants.

### Login attempts

`POST /api/auth/login`:

1. calls `ensureDatabase()`;
2. normalizes the submitted email;
3. reads `login_attempts`;
4. locks an email after 5 failed attempts for 15 minutes;
5. only accepts the hard-coded administrator email;
6. hashes the submitted password and compares it to the stored Base64 hash string;
7. deletes the attempt record after success;
8. creates a session.

The rate limit is keyed only by email, not IP/device, and unknown emails can create rows. It is useful but not a complete production abuse-control design.

### Session mechanism

- A random 32-byte token is generated with Web Crypto.
- The plaintext token is returned only in the cookie.
- Only `SHA-256(token)` is stored in `sessions.token_hash`.
- Expiration is 14 days from creation.
- Cookie name: `ops_session`.
- Cookie flags: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, explicit `Expires`.
- Session validation hashes the cookie token and performs a server-side join against `sessions` and `users`, including `expires_at > now`.
- Logout deletes the matching database session and clears the cookie.
- There is no sliding renewal, expired-session cleanup job, device list, global sign-out, or session revocation on password change.

### Server-side protection

- `GET /api/app` requires a valid database session.
- `POST /api/app` requires a valid database session and rejects all mutations while `must_change_password` is true.
- Password change requires an authenticated session and the current password.
- The root application page is not guarded by Next/Vinext middleware; it loads a client login view after `/api/auth/session` returns 401.
- There is no `middleware.ts` or `proxy.ts`.
- Sensitive data endpoints are protected server-side despite the lack of page middleware.
- Sites currently adds an owner-only platform access layer outside the application.

### Mandatory password change

The seeded admin has `must_change_password = 1`. After login, the UI opens a non-dismissible password dialog. `POST /api/app` also returns 403 until the password changes, so the restriction is not merely visual. `POST /api/auth/change-password` verifies the old password, requires at least 10 characters, generates a new salt/hash, clears the flag, and writes an activity entry.

### Auth/security findings

1. **Critical — runtime SQL identifier injection risk:** the `archive` action interpolates `body.entity` directly into `UPDATE ${body.entity}`. TypeScript types do not validate untrusted JSON at runtime. A malicious authenticated request can control this identifier. Even if D1 blocks multiple statements, arbitrary identifier interpolation is unsafe and must be replaced with a strict runtime allowlist before production use.
2. **High — sessions survive password changes:** changing the password does not invalidate existing sessions.
3. **High — fixed bootstrap hash/salt in source:** not plaintext, but the bootstrap credential design should be replaced.
4. **Medium — no constant-time hash comparison:** the implementation compares Base64 hash strings with `!==`.
5. **Medium — no explicit CSRF token or Origin validation:** `SameSite=Strict` materially mitigates ordinary CSRF, but mutation routes do not enforce Origin/CSRF independently.
6. **Medium — no request schema validation:** only a few required fields are checked; field formats, enum values, dates, money bounds, phone numbers, URLs, and identifier ownership are not comprehensively validated.
7. **Medium — no session housekeeping:** expired rows accumulate.
8. **Medium — authorization is centralized at the endpoint but not at a typed data-access layer.**
9. **Medium — runtime DDL executes during every session check**, increasing latency and coupling authentication to schema management.

The official Next.js guidance recommends using an authentication/session library for production complexity, keeping authorization close to the data source, and using secure server-set cookies: [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication).

## 8. Recurring charges

### Creating a recurrence

A charge is created in `charges` with:

- `recurring = true`;
- `recurrence_months` (default 1);
- normal charge data such as company, description, value, and due date.

There is no separate `subscriptions` table and no recurrence rule entity.

### Generating the next charge

The next occurrence is generated only when `markPaid` runs for the current charge:

1. current charge becomes `paid` and receives `paid_at`;
2. if recurring, due date is advanced by `recurrence_months` in JavaScript;
3. a new pending charge copies the company, project, description, category, value, payment method, recurrence settings, and notes;
4. the new charge references the paid charge through `parent_charge_id`;
5. `INSERT OR IGNORE` prevents duplicate generation.

Limitations:

- Future occurrences are not generated ahead of time.
- If a recurring charge remains unpaid, the next month's charge is never created.
- End-of-month arithmetic uses JavaScript `setUTCMonth`; dates such as January 31 can overflow into March instead of selecting February's last day.
- Frequency is integer months only; no custom day/week rule.
- There is no pause, cancel-at, start-at, end-at, grace period, price history, or subscription state.
- There is no separate payment table; `paid_at`, `status`, and `payment_method` live on the charge.

### Overdue calculation

Whenever `runAutomations()` executes, pending, unarchived charges with `due_at < today` become `overdue`. This does not run continuously; it only runs when an authenticated user loads `GET /api/app`.

## 9. Automatic tasks

`runAutomations(userId)` executes synchronously at the beginning of `getAppData()`.

### Charge due/overdue

- Pending charges before today are marked overdue.
- Pending or overdue charges with `due_at <= today + 3 days` generate one charge task.
- Past-due tasks are urgent; upcoming tasks are high priority.
- There is no lower date bound, so old unresolved charges remain eligible, subject to idempotency.

### Domain expiration

- Active, unarchived domains with `expires_at <= today + 60 days` generate one task.
- The task's due date is the domain expiration date.
- The requested 60/30/15/7/3/0-day sequence is **not implemented**.
- Alert thresholds are not configurable.
- Only one task is generated per domain expiration date.

### Opportunity follow-up

- An opportunity with `next_follow_up_at <= today`, not won/lost and not archived, generates one high-priority follow-up task.

### Company next action/post-sale

- A company with `next_action_at <= today` generates one normal-priority task.
- `contact_frequency_months` is stored but never used to calculate a new post-sale date.
- There is no automatic “last contact + frequency” post-sale engine.

### Post-sale limitation

Post-sale only works when a manual `next_action_at` exists. The system does not automatically schedule another contact after completing a post-sale task and does not derive it from `last_contact_at` or `contact_frequency_months`.

## 10. Task deduplication/idempotency

`tasks.automation_key` is unique. Automation inserts use `INSERT OR IGNORE`.

Keys:

- Charge: `charge:<charge_id>:<due_at>`
- Domain: `domain:<domain_id>:<expires_at>`
- Follow-up: `followup:<opportunity_id>:<next_follow_up_at>`
- Company next action: `company:<company_id>:<next_action_at>`

Recurring charge generation uses a separate unique key:

- `recurrence:<paid_charge_id>:<next_due_date>` stored in `charges.recurrence_key`.

Consequences:

- Repeated dashboard loads do not create duplicates.
- Changing the relevant due/follow-up date creates a new key and permits a new task.
- Completing an automated task does not delete its key; the same unresolved event will not create another task later.

## 11. Cron/scheduled jobs

There is no cron, Cloudflare scheduled handler, Vercel Cron, background worker, queue, or dedicated automation endpoint.

Automation processing occurs only when an authenticated user loads `GET /api/app`. Therefore:

- nothing is processed while the application is unused;
- there are no proactive emails/push messages;
- overdue states can remain stale until the next application load;
- a domain or follow-up task appears only after the dashboard data is requested.

The recommended Vercel migration should add a protected, idempotent endpoint such as `/api/cron/automations` and a daily Vercel Cron definition. Vercel Cron calls a configured production path with HTTP GET: [Vercel Cron Jobs](https://vercel.com/docs/cron-jobs).

## 17. Data export and backup status

The application has no authenticated data export, CSV download, JSON backup, database dump, or restore flow.

The Sites database viewer/connectors can read bounded pages for operational inspection, but this is not a user-controlled, versioned, comprehensive export workflow. The local `.wrangler` SQLite file contains only local QA data and is not the production D1 database.

## 18. Can this migrate without a rebuild?

Yes. This is a migration/refactor, not a zero-based rebuild.

Highly reusable:

- React components and visual design;
- Tailwind theme and responsive layout;
- form definitions and product vocabulary;
- App Router directory structure;
- most API request/response shapes;
- entity TypeScript interfaces;
- charge/task/domain business rules after correction;
- Drizzle as an ORM/migration tool;
- assets and metadata;
- current Git history.

Must be replaced or substantially adapted:

- Vinext/Vite/Sites runtime → official Next.js runtime;
- Worker `env.DB` → Neon database client;
- SQLite `sqliteTable` schema → PostgreSQL `pgTable` schema;
- raw D1 prepared statements → parameterized Drizzle/PostgreSQL queries;
- runtime `ensureDatabase()` DDL → controlled PostgreSQL migrations and seed;
- custom authentication/session implementation → hardened library or audited DAL/session layer;
- on-read automations → protected scheduled job;
- Sites access policy → application authentication/authorization only;
- Sites deployment config → Vercel project configuration;
- Sites managed remote → GitHub remote.

Official Next.js can run as a Node.js server with `next build`/`next start`, while Vercel provides the integrated deployment target: [Next.js deployment options](https://nextjs.org/docs/app/getting-started/deploying).

## 19. Migration plan: ChatGPT Sites → GitHub/Vercel/Neon

### Phase 0 — freeze and decisions

1. Keep the current Site unchanged and owner-only.
2. Do not activate the pending Sites custom domain.
3. Select authentication strategy. Recommendation: a maintained Next.js-compatible authentication library with database sessions, rather than expanding the custom implementation.
4. Decide whether to keep current string IDs or adopt PostgreSQL UUIDs. With zero production records, UUIDs are preferable.
5. Define production, preview and local environments.

### Phase 1 — GitHub ownership

1. Create a private GitHub repository owned by the user.

3. Push the existing commit and report.

### Phase 2 — official Next.js runtime

2. Add the official `next` dependency compatible with React 19.

### Phase 3 — PostgreSQL/Neon schema

1. Create a Neon project and production branch.

3. Convert `db/schema.ts` from `drizzle-orm/sqlite-core` to `drizzle-orm/pg-core`.
4. Configure Drizzle with `dialect: 'postgresql'` and `DATABASE_URL`.
5. Generate a new PostgreSQL baseline migration. Drizzle documents Neon HTTP connectivity, `DATABASE_URL`, PostgreSQL schema declarations, and generated migrations: [Drizzle with Neon](https://orm.drizzle.team/docs/tutorials/drizzle-with-neon).

6. Load parent tables first: users → companies → contacts/projects → domains/opportunities/charges → tasks/activities/templates.

8. Verify row counts per table, nullability, money totals, unique keys and FK integrity.
9. Run business checks for overdue charges, next recurrence, domain windows and opportunity stages.
10. Keep the old D1 read-only until Neon backup/restore and application behavior are verified.

## 20. Recommendation: Sites + D1 vs GitHub + Vercel + Neon

### A) Remain on ChatGPT Sites + D1

Advantages:

- already deployed;
- owner-only outer access policy;
- minimal infrastructure management;
- D1 is adequate for a small, single-user relational workload;
- very fast iteration inside the current environment.

Disadvantages for this case:

- deployment and database lifecycle are controlled through Sites rather than the user's GitHub/Vercel/Neon accounts;
- current remote is managed, not GitHub-owned;
- current production export story is insufficient;
- external integrations and scheduled processing are less conventional for the requested long-term architecture;
- the current runtime is Vinext/Worker-specific, not official Next.js on Vercel;
- platform access and app login are two separate gates;
- long-term operational control, observability and restore procedures are not yet owned by the user.

### B) Migrate to GitHub + Vercel + Neon

Advantages:

- source, deploy and database are directly controlled by the user;
- familiar GitHub versioning and review workflow;
- first-class official Next.js deployment path;
- PostgreSQL data types, constraints, tooling and ecosystem;
- Neon branching/restore capabilities;
- conventional Vercel Cron path for automation;
- cleaner future integration with Resend, WhatsApp Business and Google Calendar;
- easier provider portability and data export strategy.

Costs:

- the user becomes responsible for provider accounts, billing, secrets, monitoring and backups;
- migration and authentication hardening require focused engineering work;
- production migrations and cron jobs need disciplined operations.

### Recommendation

**Choose B: GitHub + Vercel + Neon.**

For a long-lived system containing client contacts, domains and commercial financial data, direct ownership of source, database, deployment, backup/export and integration secrets outweighs the convenience of keeping this MVP on Sites. The current zero-row production database makes now the lowest-risk time to migrate.

Do not migrate by copying the current runtime verbatim. Preserve the UI/product work, then deliberately replace the platform-specific and security-sensitive layers.

## 21. Recommended priority before real client data

1. Do not activate the Sites custom domain.
2. Decide and implement GitHub/Vercel/Neon migration.
3. Fix the critical dynamic SQL identifier issue.
4. Replace bootstrap auth constants and revoke sessions on password changes.
5. Establish migrations, backup/restore and export.
6. Add real cron automation.
7. Only then enter substantial real client/financial data and activate the final domain.
